# 架构详解

读完本文,你能理解整个项目如何工作,并知道"想改某处该看哪个文件"。

## 1. 一句话概括

Bootloader 开机后做三件事:**决定进不进入升级模式** → 升级模式下**用 YMODEM 协议可靠地接收固件并写入 Flash** → **跳转到新固件运行**。APP 是普通用户程序,附带一个"长按按键请求回到 Bootloader"的能力。

## 2. 整体架构

### 2.1 两个独立工程

```
BootLoader/
├── bootloader/   链接地址 0x08000000 (16KB)   ← ST-Link 只烧这个
└── app/          链接地址 0x08004000 (240KB)  ← 串口升级写入这个
```

两个工程**完全独立**(各自携带库和模块),但共享一套"约定":

- Flash 分区约定(地址、大小)—— 定义在 `modules/bootapi/boot_api.h`
- 备份寄存器魔数 `0xDEADBEEF` —— APP 写, Bootloader 读

### 2.2 Bootloader 内部分层

```
┌────────────────────────────────────────────────────┐
│ 应用层   core/main.c     主循环                     │
│          app/boot.c     启动决策 (进 BL 还是跳 APP)  │
│          app/updater.c  升级状态机 (等文件→收→校验→跳)│
├────────────────────────────────────────────────────┤
│ 协议层   protocols/ymodem/  纯 C, 不依赖任何硬件     │
│          接收状态机 + CRC16, 通过回调与上下层交互     │
├────────────────────────────────────────────────────┤
│ 驱动层   drivers/usart    串口 DMA 收发              │
│          drivers/flash    Flash 擦写 + 元数据        │
│          drivers/crc32    硬件 CRC32                 │
├────────────────────────────────────────────────────┤
│ 模块层   modules/board    引脚定义 (硬件差异只改这里) │
│          modules/led      状态灯                     │
│          modules/key      按键消抖                   │
│          modules/systick  1ms 节拍                   │
├────────────────────────────────────────────────────┤
│ 库       libraries/cmsis + libraries/stdperiph      │
└────────────────────────────────────────────────────┘
```

**依赖规则:上层可以调用下层,下层绝不反向依赖。** 协议层最干净——不包含任何
STM32 头文件,所以可以在电脑上跑单元测试(`tests/ymodem/`)。

### 2.3 数据流 (升级时一个字节的旅程)

```
Tera Term ──串口──> DMA 环形缓冲 ──主循环轮询读出──> ymodem_feed(逐字节)
                                                          │
                                    ┌─────────────────────┤
                                    ▼                     ▼
                            on_header 回调          on_data 回调
                            (文件名/大小/版本)      (1024 字节数据块)
                                    │                     │
                            校验大小, 标记待擦除      懒擦除 + Flash 写入
                                    │                  (写后回读验证)
                                    └─────────┬───────────┘
                                              ▼
                                     传输完成 (on_complete)
                                              │
                                     大小核对 -> 硬件 CRC32 全量校验
                                              │
                                     写元数据 (Sector 6)
                                              │
                                     延时 1s -> 跳转 APP
```

## 3. 启动决策 (复位后发生了什么)

```
                        设备复位
                           │
              ┌────────────┴────────────┐
              │ 1. 备份寄存器 == 魔数?   │── 是 ──> 原因=APP请求
              └────────────┬────────────┘          (APP 长按后触发)
                           │ 否
              ┌────────────┴────────────┐
              │ 2. 按键按住 50ms?        │── 是 ──> 原因=按键
              └────────────┬────────────┘
                           │ 否
              ┌────────────┴────────────┐
              │ 3. APP 有效?             │
              │ 元数据魔数 + 大小合法     │── 否 ──┐
              │ + MSP 在 SRAM            │        │
              │ + Reset 向量在 APP 区    │        │
              └────────────┬────────────┘        │
                    是     │                     │
              ┌────────────┴────────────┐        │
              │ 4. 发 5 秒 YMODEM 邀请   │        │
              │    ('C' 每秒一发)        │        │
              └───────┬────────┬────────┘        │
                   超时    收到文件头              │
                     │         └───────────────┐ │
                     ▼                         ▼ ▼
              ┌────────────┐            ┌──────────────┐
              │ 跳转 APP    │            │ 升级模式      │
              └────────────┘            │ 无限等待文件  │
                                        └──────────────┘
```

三种进入升级模式的方式(优先级从上到下):

| 方式 | 场景 | 体验 |
|------|------|------|
| APP 长按请求 | 设备正常运行中 | 最方便, 不需要碰复位键 |
| 按住按键 + 复位 | APP 异常/想强制升级 | 可靠, 一学就会 |
| 复位后 5 秒窗口 | APP 有效, 来不及按按键 | 需要手快, 或预先选好文件 |
| 无有效 APP | 新板/升级中断 | 自动进入, 无需操作 |

> 为什么"无有效 APP"也进升级模式?因为此时跳转 APP 只会跑飞,
> 停在升级模式等新固件是最安全的选择。

## 4. 升级流程 (YMODEM 时序)

```
Tera Term(发送端)               Bootloader(接收端)
       │                                │
       │     ← 'C' (请求传输, 每秒1次)  │
       │───────────────────────────────>│
       │ 文件头包(文件名\0大小\0...)     │
       │───────────────────────────────>│  解析文件名/大小/版本
       │     ← ACK (立即应答)            │  校验 0<size<=240KB
       │───────────────────────────────>│
       │ 数据包1 (1024B+CRC16)          │
       │───────────────────────────────>│  ★首次数据才擦除 APP 区
       │     ← ACK                      │  Flash 写入 + 回读验证
       │───────────────────────────────>│
       │ 数据包2 ... 数据包N             │  (同上, 直到全部写完)
       │     ← ACK xN                   │
       │  EOT (发送完毕)                 │
       │───────────────────────────────>│
       │     ← NAK (协议要求首次EOT要NAK)│
       │───────────────────────────────>│
       │  EOT (再次确认)                 │
       │───────────────────────────────>│
       │     ← ACK                      │
       │ 空文件头 (结束标志)              │
       │───────────────────────────────>│
       │     ← ACK                      │
       │                                │ ── 大小核对
       │                                │ ── 硬件 CRC32 全量校验
       │                                │ ── 元数据写入 Sector 6
       │                                │ ── LED 常亮 1 秒
       │                                │ ── 跳转 APP
```

**差错恢复**(全程自动,无需人工干预):

| 情况 | 处理 |
|------|------|
| 某包 CRC 错误 | NAK,发送端自动重传该包 |
| 重复包(ACK 丢失) | 再 ACK 一次,数据不重复写 |
| 等待超时(3 秒) | 重发上次响应,连续 5 次才放弃 |
| 文件超过 240KB | 直接 CAN CAN 中止,设备回到等待状态 |
| 发送端中途取消 | 设备自动重启接收流程,可再次发送 |

## 5. Flash 分区

```
0x08000000 ┌────────────────┐
           │  Bootloader    │ 16KB   Sector 0   ST-Link 烧录, 只读
0x08004000 ├────────────────┤
           │                │
           │      APP       │ 240KB  Sector 1-5  串口升级写入
           │                │
0x08040000 ├────────────────┤
           │    Metadata    │ 128KB  Sector 6   只用前 16 字节:
           │                │          ┌────────────────────┐
           │                │          │ magic   4B 有效性   │
           │                │          │ size    4B 固件大小 │
           │                │          │ crc32   4B 全量校验 │
           │                │          │ version 2B 版本号   │
           │                │          │ reserved 2B 预留    │
0x08060000 ├────────────────┤          └────────────────────┘
           │    Reserved    │ 128KB  Sector 7   未来扩展
0x08080000 └────────────────┘
```

> 为什么"APP 有效"要同时检查元数据、堆栈指针、复位向量?
> 单独任何一项都可能误判:元数据保证"确实完整升级过",向量检查保证
> "跳过去不会飞"。三重校验让跳转几乎不可能翻车。

## 6. LED 状态速查

| LED 表现 | 含义 |
|----------|------|
| 慢闪 (1Hz) | 等待 YMODEM 传输 |
| 快闪 (5Hz) | 正在接收固件 |
| 常亮 | 升级成功,即将跳转 APP |
| 心跳 (APP 运行中) | APP 正常闪烁,与 BL 无关 |

## 8. 关键设计决策 (为什么这样做)

| 决策 | 理由 |
|------|------|
| 用标准 YMODEM 而不是私有协议 | 免上位机, Tera Term/SecureCRT/minicom 都能发, 生态成熟 |
| 协议层零硬件依赖 + 回调 | 可以在电脑上单元测试; 换 MCU 协议层原样搬走 |
| DMA 环形接收 + 主循环轮询 | 不依赖 IDLE 中断分帧, 连续多包不会丢, 零拷贝 |
| TX 用 DMA + 完成中断 | 发送不阻塞主循环 |
| 懒擦除(首个数据包才擦) | 擦 240KB 要数秒, 若在文件头应答前擦, 发送端可能超时重发导致混乱 |
| 末包填充按文件大小截断写 | YMODEM 末包固定填到 1024 字节, 全写会超写 |
| CAN 检测只在包间隙 | 数据字节本身可能等于 0x18, 包内检测会误判 |
| 元数据为 APP 有效性权威 | ST-Link 直烧的 APP 没有元数据, 会被判无效 —— 避免跳进残缺固件 |
| 备份寄存器 + 软复位 | APP 请求重入 BL 的标准做法, 软复位不丢备份寄存器 |
